ACDOCA is the table behind the universal journal in SAP S/4HANA. Instead of storing finance and controlling data in separate line-item and totals tables, S/4HANA records the actual line items of General Ledger, Controlling, Asset Accounting, Margin Analysis and Material Ledger in one table. Finance and controlling report from the same data, so there is nothing to reconcile between them. You still post journal entries, run allocations and acquire assets as before; what changed is where the data lands and how you read it.

Why SAP introduced the universal journal

In SAP ECC, each component kept its own data: line items and totals in FI, separate tables in CO, Asset Accounting and Material Ledger, plus index tables for open items. Period-end closing involved reconciling these stores, and reporting across them often needed a data warehouse with many extractors.

According to SAP's training material on the concept of the universal journal, ACDOCA acts as "the definitive single source of truth for financial data". Because FI and CO use the same line items, SAP states that no reconciliation between financial accounting and controlling is necessary.

What ACDOCA brings together

  • General Ledger Accounting: all ledgers of the universal journal.
  • Controlling: actual postings to cost centres, internal orders, projects and other CO objects.
  • Asset Accounting: asset values and postings.
  • Margin Analysis (account-based profitability analysis): market segment attributes on the journal entry.
  • Material Ledger: inventory valuation, which is mandatory in S/4HANA.

Every journal entry carries the full coding block: G/L account, profit centre, segment, cost centre, order, project, market segment and more. That is why you can drill down from a balance sheet account to individual assets, or break down any income statement line by any dimension in the entry.

What happened to the old tables

SAP's Simplification List (item "Data Model Changes in FIN", SAP Note 2270333) explains the change in two groups.

Totals and index tables replaced by compatibility views

Totals tables and application index tables were removed and replaced by identically named views, so that SELECT statements work as before. Write access (INSERT, UPDATE, DELETE, MODIFY) had to be removed from SAP standard code and must be removed from custom code (SAP Note 1976487).

AreaTables replaced by compatibility views
Open item indexesBSIS, BSAS, BSID, BSAD, BSIK, BSAK, FAGLBSIS, FAGLBSAS
G/L totalsGLT0, FAGLFLEXT
Customer and vendor totalsKNC1, KNC3, LFC1, LFC3
CO totalsCOSP, COSS

Line-item tables redirected to ACDOCA

Other tables were wholly or partly replaced by ACDOCA. For these, the database interface redirects SELECTs to a compatibility view that reads from the new data model. Examples include COEP (view V_COEP), FAGLFLEXA, and the Asset Accounting tables ANEA, ANEK, ANEP, ANLC and ANLP. Again, code that writes to these tables must be adapted.

What about BSEG?

BSEG is still there and still updated. SAP's Simplification List notes that BSEG "is not (and will not be) extended" and still contains only three parallel currencies. The incompatible changes for summary and index tables and for BSEG updates are described in SAP Note 2431747.

For Material Ledger tables such as MLCD and CKMI1, the redirect to compatibility views only applied up to S/4HANA 1809. From 1909, SAP states that these tables and views are obsolete and that no read or write access is allowed.

Cost elements are now G/L accounts

One of the biggest changes for controllers: cost elements are part of the chart of accounts and are maintained in the G/L account master. There is no separate cost element master data. Each G/L account has a type, and income statement accounts have a cost element category:

  • Balance sheet account
  • Non-operating expense or income
  • Primary costs or revenue
  • Secondary costs, for internal value flows such as activity allocations, overhead and settlement

Because secondary cost elements are G/L accounts, all CO-internal actual postings are visible in the general ledger. The CO real-time integration and reconciliation ledger used in ECC to transfer these postings are no longer needed (Simplification List item "General Ledger", SAP Note 2270339).

Currencies in the universal journal

In ECC, FI supported up to three parallel currencies and CO two. In S/4HANA, currencies are configured centrally per ledger and company code in transaction FINSC_LEDGER (Simplification List item "Currencies in Universal Journal", SAP Note 2344012). ACDOCA provides these amount fields:

FieldMeaning
WSLAmount in transaction (document) currency
TSLAmount in balance transaction currency
HSLAmount in company code (local) currency
KSLAmount in global currency, defined by the controlling area
OSL, VSL, BSL, CSL, DSL, ESL, FSL, GSLEight freely defined currencies, configured per ledger and company code
CO_OSLAmount in CO object currency, where that is a separate currency

WSL, TSL, HSL and KSL are mandatory in all ledgers. You also mark which currency types are BSEG-relevant, because BSEG still only holds three. SAP states that with Universal Parallel Accounting switched on, all amount fields are fully supported in all processes from S/4HANA 2022; without it, coverage of the additional currencies varies by process. SAP's currency types lesson lists the standard types, such as 10 (company code), 30 (group) and 70 (CO object currency).

What it means for a conversion

  • Ledgers and currencies stay as they are. According to SAP, you cannot introduce new ledgers or new currencies during the migration to S/4HANA. If you need them, plan them as a separate project before or after the conversion.
  • Classic GL becomes ledger 0L. If you use the classic General Ledger, ledger 00 is migrated to the new leading ledger 0L.
  • Finance data migration is a step of its own. After the technical conversion, the finance Customizing and the General Ledger, Asset Accounting, Controlling and Material Ledger data must be migrated to the new structures (SAP Note 2332030). Our S/4HANA migration checklist shows where this fits.
  • Clean up first. Inconsistencies in the G/L, assets and Material Ledger cause problems in this migration; fix them in ECC beforehand.

Custom code and reporting

Custom code

  • Programs that read the old tables generally keep working through the compatibility views, but performance can differ, so test heavy reports.
  • Programs that write to totals, index or redirected tables must be changed.
  • New reports should read ACDOCA, or better, SAP's released CDS views, rather than the compatibility views. That keeps the code in line with clean core principles.

Reporting

Classic Report Writer and Report Painter reports still work, but they show the data in separate views: FI reports show the fields formerly in FAGLFLEXT, and CO reports the fields formerly in COSP and COSS. To see the combined data, SAP recommends the Fiori reports that use all the fields of the universal journal. Journal entries themselves are typically posted with the Post General Journal Entries app, with templates for recurring entries.

Common misunderstandings

  • "BSEG is gone." It is not; it is still updated and still limited to three currencies.
  • "We can redesign ledgers during the conversion." Not in the conversion itself; plan it separately.
  • "Compatibility views mean custom code needs no work." Reads usually work; writes do not, and performance needs testing.
  • "The universal journal replaces controlling." CO processes such as allocation and settlement still exist; their results are simply stored in the same table as FI.

Key takeaways

  • ACDOCA is the single line-item table for GL, CO, Asset Accounting, Margin Analysis and Material Ledger.
  • Totals and index tables became compatibility views; line-item tables such as COEP and ANEP are redirected to ACDOCA. BSEG remains.
  • Cost elements are G/L accounts with a cost element category.
  • Currencies are configured per ledger in FINSC_LEDGER, with up to eight freely defined currencies beyond the mandatory ones.
  • Plan ledger or currency changes outside the conversion, and adapt custom code that writes to old tables.

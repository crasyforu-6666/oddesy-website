"Clean core" has become one of the most important ideas in SAP S/4HANA projects. It is SAP's recommended way to keep your ERP system stable, upgradeable and ready for innovation, while still meeting requirements that standard SAP does not cover.

What does clean core mean?

A clean core is an SAP system that stays as close to standard as possible. Instead of modifying SAP's own code or building tightly coupled custom objects inside the ERP, extensions are built on stable, released interfaces, either side by side on SAP Business Technology Platform (BTP) or in-stack using modern, upgrade-safe ABAP.

Clean core is not only about code. It also covers:

  • Processes: adopting SAP best practices where they fit.
  • Data: good master data quality and governance.
  • Integration: using released APIs and standard integration tools.
  • Operations: keeping the system current and well documented.

Why it matters

  • Faster, cheaper upgrades. Fewer modifications means less testing and fewer surprises with each release.
  • Access to innovation. New SAP features and AI capabilities are easier to adopt on a standard system.
  • Lower total cost of ownership. Less custom code to maintain and support.
  • Cloud readiness. S/4HANA Cloud, and especially the public edition, requires a clean-core approach.

Where should extensions live?

Key user extensibility

Custom fields, simple logic and forms created with SAP's in-app tools. Ideal for small, business-driven changes.

Developer extensibility (ABAP Cloud)

In-stack development using the ABAP RESTful Application Programming Model and released APIs only. Suited to extensions that need to be close to SAP data and processes.

Side-by-side extensibility on SAP BTP

Separate applications, workflows and portals that connect to S/4HANA through APIs. Best for customer and supplier portals, mobile apps, complex workflows and anything that changes often.

How to move towards a clean core

  1. Measure usage. Identify which custom objects are actually used. Unused code can often be retired.
  2. Classify what remains. Decide what can be replaced by standard functionality, rebuilt on released APIs, or moved to BTP.
  3. Set governance. Define development guidelines and a review process so new code follows clean-core rules.
  4. Improve step by step. Clean core is a journey: tackle the highest-value areas first, often during an S/4HANA move.

Clean core extensibility levels

SAP now describes extensions in terms of how upgrade-safe they are. In simple terms:

  • Fully clean: extensions that use only released, stable APIs and extension points, such as ABAP Cloud development, key user tools and side-by-side BTP apps.
  • Conditionally clean: classic extensions that use well-established but not formally released interfaces. These are acceptable in private edition but carry some upgrade risk.
  • Not clean: modifications to SAP code and use of internal objects that SAP may change at any time. These should be reduced over time.

Classifying your current custom code against these levels is a practical first step and shows where the biggest upgrade risks are.

Clean core and AI

SAP's AI capabilities, including the Joule assistant and embedded AI scenarios, work best on standard processes and well-governed data. Heavily modified systems make it harder to adopt these features because the AI depends on SAP's standard data model and business logic. A clean core is therefore not just about cheaper upgrades; it is also the foundation for using AI in day-to-day operations.

Measuring progress

  • ABAP Test Cockpit (ATC) checks configured for cloud readiness show which objects use non-released APIs.
  • Usage data from your system shows which custom objects nobody uses any more.
  • Modification counts and the number of changes needed at each upgrade are useful trend indicators.
  • Upgrade effort itself: if each upgrade gets faster and needs less testing, your core is getting cleaner.

Common objections, answered

"Our processes are unique, so we need custom code." Some are, and those deserve investment. Many are not, and standard functionality now covers far more than when the original code was written.

"BTP adds cost and complexity." It can, if used for everything. Use it where side-by-side makes sense, such as portals, mobile apps and fast-changing logic, and keep simple extensions in-stack with ABAP Cloud.

"We will clean up after the migration." In practice, the migration is the best moment, because custom code must be analysed and adapted anyway.

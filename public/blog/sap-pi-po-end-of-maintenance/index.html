SAP PI/PO End of Maintenance: What 2027 and 2030 Mean and How to Move to SAP Integration Suite

Mainstream maintenance for SAP Process Orchestration 7.5 ends in 2027. Here is what that means, what SAP's assessment and migration tools can and cannot do, and how to plan the move.

By the Oddesy Consulting and Services team · 18 Nov 2026

If your company runs SAP Process Integration (PI) or SAP Process Orchestration (PO), the key date is the end of 2027. That is when mainstream maintenance for SAP NetWeaver 7.5, and therefore for PI and PO 7.5, ends. Extended maintenance is available until the end of 2030. The software will not stop working on 1 January 2028, but every year you stay on it, you run your interfaces on a platform SAP is winding down. SAP's successor is SAP Integration Suite, and SAP provides tools to assess and partly automate the move.

The dates, and what they actually mean

DateWhat happensWhat it means for you
Until end of 2027Mainstream maintenance for SAP NetWeaver 7.5, including PI and PO 7.5Normal support, fixes and updates under your existing contract
2028 to end of 2030Optional extended maintenanceSupport continues if you buy it; plan to finish migrating in this window at the latest
After 2030Extended maintenance endsTreat 2030 as the hard planning limit and confirm any remaining options with SAP

SAP's training material for the migration states the reason plainly: SAP NetWeaver 7.5 is supported in mainstream maintenance until the end of 2027, with the option of extended maintenance until the end of 2030 (SAP Learning). The same 2027/2030 pattern applies to SAP ECC, which we cover in our guide to ECC end of maintenance. Maintenance terms are contract-specific, so check SAP Note 1648480 and speak to SAP before committing to a timeline.

Older releases, such as PI 7.31 and 7.40, have their own maintenance dates. If you still run one of them, check its status in the SAP Product Availability Matrix now.

Why waiting is risky

  • Interfaces are business-critical. Orders, invoices, bank files and warehouse messages often all pass through PO. An unsupported integration layer is a risk to the whole business, not only to IT.
  • Migration takes longer than expected. Every interface has to be assessed, rebuilt or migrated, tested end to end with partners, and cut over. Large landscapes take many months.
  • It interacts with S/4HANA. Many companies are converting ERP at the same time, so integration work competes for the same people and test windows. Our S/4HANA migration checklist shows where interfaces fit.

Your target options

SAP Integration Suite (cloud)

Integration Suite runs on SAP Business Technology Platform. Besides Cloud Integration (the successor to PO's message processing), it includes API management, event-driven integration, B2B trading partner management and pre-built integration content for SAP and non-SAP applications. For most companies this is the main target.

Edge Integration Cell (hybrid)

Some interfaces must stay inside the company network, for security, compliance or because both ends are on premise. Edge Integration Cell lets you design and monitor integrations in Integration Suite while deploying and running them in your private landscape. SAP explicitly positions it as a migration path for PI customers with ground-to-ground scenarios. It does not yet match Cloud Integration feature for feature: SAP lists restrictions, including B2B scenarios and monitoring, the partner directory, the RFC receiver adapter and custom or partner adapters. Check SAP Note 3391207 for the current list before you design around it.

Third-party integration platforms

Some organisations use the deadline to review their integration platform more widely. That is a valid choice, but weigh it against the SAP-specific content, adapters and tools you would give up.

How SAP's migration tools work

SAP provides two capabilities in Integration Suite, which should be used in this order.

1. Migration Assessment

Migration Assessment connects to the Enterprise Services Repository and Integration Directory of your PO system and extracts your design-time objects. According to SAP Learning, it then:

  • evaluates each scenario for migration status, showstoppers and possible workarounds;
  • estimates the effort for each integrated configuration object (ICO) as a T-shirt size;
  • supports PO 7.31 SP28 and above, 7.40 SP23 and above, and 7.50 SP06 and above.

It must be activated in the SAP BTP cockpit, and users need the right authorisations. Connectivity to the on-premise PO system goes through SAP Cloud Connector.

2. Migration Tooling

Migration Tooling is a pattern-based feature in Cloud Integration that generates integration flows from your PO objects using templates. SAP describes it as semi-automated: where a scenario matches a supported pattern, much of the work is automated, but manual changes may still be needed. According to SAP Learning, the current scope is:

  • Objects: integrated configuration objects (ICOs).
  • Channels: HTTP, REST, SOAP, IDoc, FTP, XI and SFTP.
  • Flow steps: message mapping, Java mapping, XSLT mapping, function libraries, imported archives, XML/JSON converters and routing.
  • Events: timer.

Anything outside that list, such as other adapters or classic configuration scenarios that are not ICOs, needs more manual effort. Check the current scope in SAP's Migration Tooling documentation, because SAP extends it over time.

Technical topics that need special attention

ABAP proxies

ABAP proxy interfaces can be migrated using the XI adapter in Integration Suite and continue to run. SAP lists limitations, however: proxy generation with SPROXY against Cloud Integration is not supported, acknowledgements are not supported, and Exactly Once In Order (EOIO) is not supported without a custom solution. Plan where you will maintain proxy definitions once the Enterprise Services Repository is gone.

Java mappings

Small Java mappings can be rewritten as Groovy scripts; more complex ones can sometimes be reused through a Groovy script wrapper. SAP warns that some use cases may not work with the wrapper, including binary attachments, Microsoft Office documents, encryption and decryption, mapping lookups, file system operations, message signing and dynamic headers. Retest every migrated mapping.

Asynchronous processing

Cloud Integration offers a pipeline concept that mimics PO's processing pipelines for asynchronous scenarios, which helps when you migrate many similar interfaces.

Custom adapters

Custom or partner adapters built for PO do not move across automatically. Each one needs a replacement plan.

A practical migration plan

  1. Inventory the landscape. List every interface with its sender, receiver, adapter, volume, business owner and criticality. Mark the ones that are no longer used.
  2. Run Migration Assessment to classify each ICO and size the effort.
  3. Decide the target per interface: Cloud Integration, Edge Integration Cell, SAP pre-built content, or retire. SAP notes that pre-built content for S/4HANA can remove the need to migrate some scenarios at all.
  4. Stop building on PO. SAP recommends that new integrations, even with ECC, be built on Integration Suite to avoid adding to the migration backlog.
  5. Choose an approach: move interfaces as they are (brownfield), redesign them (greenfield), or combine the two. Most landscapes end up mixed.
  6. Migrate in waves, starting with simple, high-volume patterns that the Migration Tooling supports, to build skills and templates.
  7. Test end to end, including partners, error handling, monitoring and alerting, not only message mapping.
  8. Run in parallel during the transition. SAP expects many customers to run PO and Integration Suite side by side until migration is complete.
  9. Decommission PO once the last interface has moved and the support model for Integration Suite is in place.

Common mistakes

  • Treating it as a technical lift and shift. Many interfaces can be simplified or replaced by standard APIs.
  • Skipping the inventory. Unused and undocumented interfaces inflate the scope and the test effort.
  • Assuming the tools migrate everything. They speed up supported patterns; the rest is project work.
  • Forgetting operations. Monitoring, alerting, certificate handling and transports work differently on Integration Suite, so plan the support model early.
  • Leaving it until 2030. Extended maintenance buys time at extra cost; it is not a plan.

Key takeaways

  • PI/PO 7.5 mainstream maintenance ends at the end of 2027; extended maintenance runs to the end of 2030.
  • SAP Integration Suite is the successor; Edge Integration Cell covers scenarios that must run on premise, with some restrictions.
  • Migration Assessment sizes the work; Migration Tooling automates supported ICO patterns. Proxies, Java mappings and custom adapters need attention.
  • Start with an inventory, build new interfaces on Integration Suite now, and migrate in waves.

Frequently asked questions

When does SAP PI/PO maintenance end?

SAP PI and PO 7.5 follow SAP NetWeaver 7.5: mainstream maintenance until the end of 2027, with the option of extended maintenance until the end of 2030. Confirm the details for your contract in SAP Note 1648480 and with SAP.

Will SAP PO stop working after 2027?

No. The software does not switch off when mainstream maintenance ends, but standard support changes unless you take extended maintenance. The risk is running a critical integration platform with shrinking support.

What replaces SAP PI/PO?

SAP positions SAP Integration Suite, on SAP Business Technology Platform, as the successor. For scenarios that must run inside your own network, Integration Suite offers Edge Integration Cell, a runtime you deploy in your private landscape while design and monitoring stay in the cloud.

Can SAP PO interfaces be migrated automatically?

Partly. SAP's Migration Assessment estimates effort per integrated configuration object, and the Migration Tooling in Cloud Integration can generate integration flows from supported ICOs. Unsupported adapters and steps, many Java mappings and some ABAP proxy features still need manual work.
